# ROADMAP

> 目标不是「让机器人能回话」，而是「让她像一个住在群里的、有自己输入和想法的存在」。
> 每个阶段都能独立上线、独立回滚，验收不通过就不进下一阶段。

当前版本：**v1.0.0**（见根目录 `VERSION`）。下面的 S0–S5 是 v1.1.0 → v1.6.0 的候选内容。

## 设计约束（先定死，后面都按它来）

1. **接入层可替换**：大脑只对传输层暴露 `POST /turn`、`GET /proactive`，换框架不重写业务。
2. **人格不外包**：system prompt 的拼装权在我们手里，框架只负责搬运消息。
3. **红线**：不代发、不点赞、不评论任何平台内容；只读、只记。
4. **可观测**：每次「说 / 不说」都写 `logs/decisions.jsonl`，每次 LLM 调用都写 `usage.jsonl`。
5. **单实例**：同一 QQ 号同一时间只跑一套消费端（本机桌面端 / 云端二者取一）。

## S0 · 可观测与工具化骨架（v1.1.0，约 1 天）

- `cloud/lib/llm.mjs`：`chatCompletion()` 返回 `usage`（prompt/completion/cacheHit/cacheMiss），
  每次成功调用追加一行到 `data/usage.jsonl`（不记正文）。
- 新增 `data/decisions.jsonl`：主动说话的每个 gate / 每次工具调用都留痕（与 `trace.jsonl` 合并或并存）。
- 定义 `POST /turn` 契约：`{conv, kind:'private'|'group', text, images?, sender}` → `{segments:[{type:'text'|'image'|'at',...}], think?}`；
  桥（或未来的框架适配器）只做搬运。
- 指令 `/用量`（今日 / 区间 / 按场景）、`/余额`（DeepSeek `/user/balance`）。
- 顺手省一笔：`prompt.mjs` 的时间上下文从「精确到分钟」降到「时段 + 日期」，让前缀缓存命中。

**验收**：现有行为零回归；`usage.jsonl` 能对上官方账单；`/用量` 与 `/余额` 可用。

## S1 · agent loop（v1.2.0，约 2–3 天）

- 工具集 v1（最多 3 步，每步 20s 超时，超时即降级为纯聊天）：
  `web_search` / `read_url` / `send_meme` / `remember` / `recall`；**视觉工具预留接口，本版不启用**。
- 工具调用写 `decisions.jsonl`（工具名、参数摘要、耗时、是否采用结果）。
- 触发纪律：仅当用户明确提问「查一下 / 是什么 / 怎么回事」或需要事实核对时才调工具，闲聊绝不调。

**验收**：20 条真实提问 A/B（有无工具）人工盲评；平均延迟增加 < 3s；不出现「工具失败还硬编答案」。

## S2 · 群聊注意力（v1.2.0 已上线，约 2–3 天）

- 群旁听缓冲（最近 20 条、只保留文本与发言者昵称），三种触发：
  被点名（+20）、话题命中语义记忆（+15）、气氛正向（+5）；基础速率 +3/h。
- 发言前三次 LLM：**旁听评分**（0–10，<7 放弃且 `impulse -= 30`）→ 起草 → 自检。
- `annoyance` 反感度：显式制止 +40、说完 3 分钟无人接 +10、群友抱怨 +50、被踢/禁言/撤回 +80；
  ≥60 该群冲动归零 + 冷却 12h，≥100 冷却 7 天并写进自我模型。
- 硬上限：阈值 120、消耗 120、**每群每日 1 条**、同群最小间隔 6h；静默 23:30–07:30 共用。
- 指令 `/闭嘴`（该群永久静音，写 `rules[]`）。

**验收**：连续一周真实群跑，日均主动发言 ≤ 1/群，0 次被踢/被投诉，`trace.jsonl` 每条都有可解释理由。

## S5 · 记忆管理（v1.6.0 已上线，约 2–3 天）

> **2026-10-24 实现**：`cloud/lib/memory-manager.mjs`（L2 压缩摘要落盘 `data/summaries/`、
> 摘要的摘要、按轮截断兜底、自我模型 `data/self.json` 带 24h/drift 双闸）+ `cloud/lib/semantic.mjs`
> 重写（importance / lastUsedAt / 关键词 recall / 衰减归档 `data/archive/`）+ `/记忆` 显示摘要、
> `/忘记 <词>`、`/我是谁`。自测覆盖压缩落盘、摘要复用、检索、遗忘。

参考 AstrBot 的上下文压缩机制（`astrbot/core/agent/context/compressor.py`），但补上它没有的「长期记忆」。
AstrBot 的做法可以概括成三件事：

1. **触发**：按 token 用量比例判断，`current_tokens / max_tokens > 0.82` 才压缩（`compression_threshold=0.82`）；
2. **切分**：按「轮」切，保留最近的约 **15%** token（`keep_recent_ratio=0.15`，上限 0.3），
   最新一轮永远原样保留；
3. **压缩**：把更早的轮次喂给 LLM 生成摘要（提示词要求「可无缝接着干活」，并明确「若任务进行中，
   结尾写上最新状态」），然后把结果拼成一对消息注入：
   `user: "Our previous history conversation summary: …"` + `assistant: "Acknowledged the summary…"`，
   最后接上保留的最近轮次。
   另有兜底实现 `TruncateByTurnsCompressor`（直接丢最早若干轮），以及基于估算的 `TokenCounter`。

我们要做的（三层 + 遗忘）：

- **L1 情节记忆**：近 N 轮原样（保持现在行为）；
- **L2 压缩摘要**：超过阈值时把更早的轮次压成「记忆摘要」，**落盘持久化**并按会话分桶
  （`data/summaries/<conv>.json`：`{summary, coveredUntil, updatedAt, tokens}`），每轮注入；
  摘要本身再超长时做「摘要的摘要」（AstrBot 没有这一层）；
- **L3 语义记忆**：事实/偏好/事件（人、喜好、约定、看过的内容），带 `importance` 与 `lastUsedAt`，
  检索用关键词 + 向量混合（先关键词，量大了再上 embedding）；
- **自我模型**：≤200 字的「我是谁 / 我和主人到哪一步了」，每次对话注入，只允许缓慢变化（防人格漂移）；
- **遗忘曲线**：`importance` 随使用衰减，30 天未命中的低分记忆降级归档（不删除，落 `archive/`）；
- **可解释**：`/记忆` 显示摘要与命中条目，`/忘记 <关键词>` 定点删除，`/记忆导出` 走备份服务。

**验收**：连续 300 轮对话后，机器仍记得早期关键事实（人名、约定、偏好）；
压缩后 system+摘要+最近的总 token 稳定在上限 70% 以内；人格与口癖无明显漂移（A/B 盲评）。

## S6 · 让她自己长（Letta，试运行中）

> 2026-10-30 起试运行。详细方案与操作手册见 [`docs/LETTA.md`](./LETTA.md)，当日工作记录见 [`docs/2026-10-30.md`](./2026-10-30.md)。

**为什么要转**：S0–S5 做完之后，她的「人格」仍是我们写的先验——写得再细，也是照着演。
用户要的是「给一个起点，看她自己长成什么样」。差别不在记忆多少，而在**谁有权改写「她是谁」**。

**做法**：

- 人格 / 对主人的认识 / 记忆都放进 Letta 的**可写记忆块**，她自己用 `memory_insert` / `memory_replace` 改；
- 红线单独一块（`safety`）**只读**：不泄密钥、不冒充真人、不代发违规、只有主人能改；
- **动机仍在我们这层**：什么时候想开口由 scheduler 决定，说什么由 Letta 决定；
- 接入方式：`behavior.letta.convs` 白名单 + SSH 反向隧道，命中才走 Letta，失败回落原引擎。

**已完成的 P0（当晚）**：

- QQ 私聊与群 `1106592574` 试运行接线完成，回落在日志可查。

**P1 / P2（2026-10-31 完成）**：审计与回滚（`letta-audit.mjs` + `/她改了啥` + `/回滚`）、动机接入（`wakePrompt` / `SKIP` / 回落）。

**下一步**：P3 —— 跑几天看这四条验收，再决定是否把主脑换成 Letta。

**验收（不看「像不像人」，看这四条）**：承诺兑现率、纠错复现率、事实一致性、主动行为有无前因。

## 语音（TTS）选型 · 现状 Edge TTS vs 候选 Breeze TTS

> 2026-10-31 写入计划，**尚未实施**。结论先放这儿：Edge TTS 继续当默认，Breeze TTS 值得拿私聊做一次 A/B。

### 现在的方案（v1.14.0 线上）

- 引擎：微软 **Edge TTS**（`edge-tts 7.3.1`，命令行子进程），音色 `zh-CN-XiaoyiNeural`。
- 流程：生成整段 mp3 → base64 → OneBot `record` 段。**不是流式**。
- 实测（腾讯云服务器，18 个汉字）：**1.39 / 1.55 / 1.77 秒**，23.6KB mp3。
- 优点：**免费**、无需 key、大陆直连稳定、已经接好回落逻辑。
- 缺点：只有一个「播音腔」音色；**没有情绪控制**（只能靠标点和语气词）；非流式，长句要等整段。

### 候选：Breeze TTS（BreezeBlue）

- 定位：**指令遵循的语音模型**（audio language model，文本+音频交错序列训练）。两条能力线：
  1. **音色设计**——用自然语言描述角色身份/语气/场景，直接生成新音色（不需要参考音频）；
  2. **演绎控制**——给一段参考语音，用指令改它的情绪/语气，同时保持音色身份（引导强度可调）。
- 官方基准：`InstructTTSEval` 上（声学参数 / 描述式风格 / 角色扮演三类各 1000 条）自称领先；延迟榜 **TTFA p50 127ms / p95 159ms**（WebSocket 持久连接、英文长句、美国三区域、最高优先级队列）。
- 价格：**$30 / 100 万加权字符**；中日韩文字**每个字算 2 字符**；免费 400 积分/天（≈ **2000 汉字/天**）；$9/月 Starter 起。
- 接口：REST（`/v1` 有 models / text-to-speech / stream / realtime session / voices / 克隆与设计预览 / 用量查询），`api.breezeblue.ai` 从我们服务器**直连可达**（无 key 返回 401，0.83s）。
- 官网：[Breeze TTS 研究页](https://breezeblue.ai/zh/breeze-tts-1)、[延迟基准](https://breezeblue.ai/zh/benchmarks/tts-latency)、[定价](https://breezeblue.ai/zh/pricing)、[API 文档](https://docs.breezeblue.ai/api-reference/introduction)。

### 对比表

| 维度 | 现在：Edge TTS | 候选：Breeze TTS 2 |
|---|---|---|
| 音色 | 1 个固定（可选择其它系统音色，但都是播音腔） | **文本描述设计音色** + **参考音频克隆** |
| 情绪 / 演绎 | 无，只能靠标点与语气词 | **指令控制**（角色扮演、场景、情绪强度） |
| 延迟 | 实测 1.4–1.8s（含起子进程 + 整段下载） | 官方 TTFA p50 **127ms**、p95 159ms（流式） |
| 流式 | ❌ 整段 | ✅ WS 流式 + 实时会话 |
| 成本 | **0** | $30/100 万加权字符；≈ **$2/月**（按每天 30 条 × 40 汉字估） |
| 中文效果 | 已验证稳定，多音字偶错 | **未验证**（官方基准以英文为主，需实测） |
| 稳定性 | 免费公用端点，偶发失败（已有回落） | 商业 API，按套餐限并发 |
| 数据合规 | 文本发微软 | 文本发**境外第三方**（内容出境） |
| 接入成本 | 子进程，约 60 行（已完成） | REST/WS + key，约 100 行 |

**成本推算**：每天 30 条语音 × 40 汉字 = 1200 汉字 → 2400 加权字符/天 → 每月约 7.2 万 → **$2.2/月**；免费额度（2000 汉字/天）基本够试运行。

### 开源自托管候选（免费，但要 GPU）

结论：**有，而且能力已经追上**——只是全部需要 GPU（4–6GB 显存起步），我们 2C2G 的云服务器跑不动。

| 模型 | 文本造音色 | 指令控情感 | 中文 | 许可 | 硬件 | 备注 |
|---|---|---|---|---|---|---|
| **Qwen3-TTS**（阿里，1.7B / 0.6B） | ✅ `VoiceDesign` 模型 | ✅ `CustomVoice` 9 个预置音色 + 文字指令 | ✅ 原生，10 语言 | Apache-2.0 | 1.7B 约 5–6GB、0.6B 约 3.5–4GB | 三种模式分开出模型；官方称首包 97ms，但消费级 GPU 上**一句 10–20 秒** |
| **IndexTTS-2**（B 站） | ❌（靠参考音频） | ✅ 情绪控制（情感参考/描述，需实测版本差异） | ✅ | 开源（见仓库） | 需 GPU | 情感表现力强，工业级零样本 |
| **MOSS-VoiceGenerator**（OpenMOSS） | ✅ 自然语言描述造音色 | 部分 | 需实测 | Apache-2.0 | 需 GPU | 专做「文字→音色」 |
| **CosyVoice 2/3**（阿里 FunAudioLLM） | 部分（instruct） | ✅ instruct 指令（情感/方言/语速） | ✅ | Apache-2.0 | 需 GPU | 生态成熟、推理脚本多 |
| **Spark-TTS** | ❌（属性控制：性别/音高/语速） | 部分 | ✅ | 开源 | 需 GPU | 不是自由文本描述 |
| **GPT-SoVITS v4** | ❌ | 参考音频控情绪 | ✅ | 开源 | 需 GPU | 社区最大，克隆效果好 |

**为什么现在不能直接换上**：

1. **硬件**：2C2G、无 GPU 的云服务器跑不动任何一条；本地 PC 若没有独显也不行（4GB 显存是底线）。
2. **速度**：消费级 GPU 上一句 10–20 秒；聊天里「文字已经发出去了，语音 15 秒后才到」可以接受（语音当补充），但实时对讲不行。
3. **运维**：要自己拉起推理服务（vLLM-Omni / ComfyUI / Gradio），比 `edge-tts` 一条命令复杂得多。

**可行路线（按代价从低到高）**：

- **A（0 成本试听）**：Colab 免费 T4 跑 `Qwen3-TTS-12Hz-1.7B-VoiceDesign`，用一句「蓝发鲸鱼女仆，声音软、说话慢、偶尔犯困」造出她的音色，先听像不像；
- **B（本机常驻）**：家里有独显 → 本机跑 Qwen3-TTS 服务，云端把文本经隧道丢过来取 mp3（复用 Letta 那条隧道思路）；
- **C（租 GPU）**：按小时租一张 3060/4090（几元到十几元/小时），只在要试音色时开；
- **D（商用 API）**：Breeze TTS / 通义 DashScope，$2/月级别，零运维——这就是上面那节在评估的路线。

**建议顺序**：先 A 造音色试听（几乎零成本）→ 决定声音像不像 → 再在 B/D 之间选一条常驻。

### 分阶段计划

- **P0（已完成）**：Edge TTS 上线，`shouldSpeak()` 闸门 + 语音失败回落文字。
- **P1（半天）**：`cloud/lib/tts.mjs` 抽 `provider`（`TTS_PROVIDER=edge|breeze`），Breeze 接 `POST /v1/text-to-speech`，用**免费额度**在私聊跑 20 条固定句子 A/B（同文本、同场景），只记录不切换。
- **P2（1 天）**：盲评胜出则切换默认；把**情绪接进语音**——`moodBrief` 的心情映射成 instruction（`低落→压低声音、慢一点`、`困→含含糊糊`、`高兴→轻快上扬`），每条语音带指令；失败仍回落 Edge。
- **P3（可选）**：**音色设计**——用她自己的设定生成专属音色并固定成 voice id（写进 `pet.json`），从此「她的声音」是稳定的、属于她的，而不是借来的系统音色。
- **自托管路线（不推荐）**：开源的 `BreezyVoice`（MediaTek Research，CosyVoice 底座）需要 GPU，2C2G 跑不动 → 只在将来有 GPU 机器时再考虑。

### 验收（换不换看这四条）

1. 中文盲评 ≥ 现在（5 分制，10 条样本，你听不署名）；
2. 端到端 TTFA < 800ms（我们自己的网络与链路，不是官方美国区数据）；
3. 失败率 < 2%（失败必须自动回落 Edge，用户无感）；
4. 每月成本 < $5，且不出现「读错多音字 / 语气词怪 / 断句错」的明显问题。

### 待核实（P1 开工前）

- Breeze TTS 的**中文支持范围**（模型列表里的语言字段、是否支持 zh-CN 与中文多音字）；
- 免费套餐注册是否需要手机/信用卡验证；
- 情绪 instruction 对**中文**的实际作用强度（英文示例不能直接外推）；
- 我们这条链路（腾讯云 → 海外 API）的真实合成延迟，不能拿官方美国区 127ms 当承诺。

### 风险

- 中文语音质量与多音字处理**没有公开验证**，必须先盲测；
- 海外 API：延迟抖动、限流、条款变更；文本出境（聊天内容）需你知情同意；
- 内容审核可能误杀「傲娇/怼人」台词；
- key 管理与计费，别把 key 写进仓库（沿用 `.env` 那套）。

## 排期顺序

```
S0 ──► S1 ──► S2 ──► S3 ──► S4 ──► S5 ──► S6 ──► S7
 │      │      │      │      │      │      │      │
 账本   能力   群聊    输入   多平台  记忆  自我演化  声音
```

S7（语音换型：Edge → Breeze TTS 或自建）是可选项，只在 S6 稳定后再动，详见下方「语音（TTS）选型」。

S6 与 S1/S4 并行推进：S1 的 agent loop 可以交给 Letta 的工具层，S4 的 `/turn` 契约正好是「换大脑」的接口。

- S0/S1 是「能不能帮忙」的地基，先做；
- S2 是「像不像群友」的关键，做完就该在真实群里试一周；
- S3/S5 决定「她有没有自己的生活」；
- S4 只在需要多平台或想要控制台时才做，属于可选项。

## 明确不做

- 抖音客户端自动化、任何平台代发 / 点赞 / 评论；
- 2C2G 机器上跑无头浏览器（内存不够，真浏览需先升 4G）；
- 把人格 / 主动性外包给框架的默认 agent。
